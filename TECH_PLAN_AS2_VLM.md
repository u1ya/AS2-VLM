# Технический план: языковое управление Unitree AS2 EDU

## 1. Цель и границы MVP

Реализовать выполнение текстовых инструкций из одного или двух последовательных действий в одной комнате. Цель должна быть видна сейчас либо обнаруживаться ограниченным поворотом на месте. Использовать готовую VLM без обучения на первом этапе.

Поддерживаемые примеры:

- «Дойди до белой стены».
- «Дойди до двери».
- «Оглянись вокруг».
- «Повернись в сторону мужчины».
- «Повернись к двери и подойди к ней».
- «Пройди вперёд на метр и остановись».

В MVP не входят переходы между комнатами, поиск по всему зданию, открывание дверей, лестницы и преодоление препятствий. Для подхода к двери выбирается свободная точка перед ней; робот не проходит через закрытую дверь. Для подхода к человеку нужны отдельные настройки дистанции.

Завершение каждого приказа имеет статус SUCCEEDED, FAILED или CANCELLED с машинно-читаемой причиной. Остановка также выполняется автоматически в конце движения.

## 2. Решения перед написанием кода

Сначала заполнить `docs/hardware_inventory.md` по реальному роботу:

| Что проверить | Что зафиксировать | Что зависит от результата |
|---|---|---|
| AS2 EDU и прошивка | Модель, версия, документация | Совместимость SDK |
| Вычислитель | ОС, архитектура CPU, RAM, свободный диск | Сборка и установка |
| RGB | API, формат, частота, задержка, калибровка | Визуальное обнаружение |
| LiDAR / depth | API, формат, частота, система координат | Дистанция и препятствия |
| Одометрия и IMU | Доступность, частота, системы координат | Повороты и ходьба |
| Управление | Рабочие методы SDK, частота команд, возврат управления оператору | Robot bridge |
| Сеть | IP, интерфейс, доступ по SSH, канал до GPU | Деплой и связь |
| Запуск сервисов | systemd либо другой механизм | Автозапуск |

Не переносить IP, имена topics, номера режимов походки и команды Go2 в AS2 без проверки. Наличие метода в заголовке SDK не доказывает его работоспособность на конкретной прошивке.

Блокирующее условие для автономного подхода: отсутствуют метрическая глубина/LiDAR или надёжная обратная связь о движении. В таком случае сначала реализуются понимание приказов и повороты; недостающие сенсоры или оценивание положения добавляются до ходьбы к объектам.

## 3. Архитектура и размещение

```text
GPU-компьютер:
  CLI/API -> instruction parser -> visual grounding -> task executor
                                      ^                   |
                                  RGB/history        skill request
                                      |                   v
Робот или подключённый onboard-компьютер:
  sensor adapter -> calibrated observations -> local motion controller
                                                     |
  remote requests -> validator -> watchdog -> AS2 SDK bridge
                                                     |
                                             штатная locomotion
```

VLM запускается на внешнем GPU. На onboard-компьютере работают приём сенсоров, проверка препятствий, контроллер движения и watchdog. Если установка на штатный вычислитель не поддерживается, использовать отдельный установленный на роботе компьютер; не менять системное ПО производителя.

Для MVP достаточно небольших HTTP API для приказов и состояния, а также потока кадров. Ограничить очередь RGB одним последним кадром. Запросы на движение имеют короткую аренду управления и уникальный ID; повторная отправка ID не запускает действие заново. Не создавать интернет-доступный управляющий endpoint.

ROS 2 использовать, если рабочие драйверы AS2 уже доступны у команды. Внутренние интерфейсы должны позволять заменить HTTP transport на ROS 2 без изменения навыков. Версию ROS/ОС выбирать после проверки vendor SDK.

## 4. Репозиторий

```text
as2-vlm/
  apps/operator_cli/          # приказ, статус, отмена
  services/model_server/      # VLM, parser, grounding
  services/task_executor/     # очередь и автомат состояний
  robot/bridge_cpp/           # адаптер официального SDK AS2
  robot/sensor_adapter/       # RGB, LiDAR/depth, odometry, IMU
  robot/motion_controller/    # yaw, distance, approach, watchdog
  common/schemas/             # версионируемые контракты
  configs/                   # example-конфиги без секретов
  deploy/                    # сборка, установка, сервисы, rollback
  tools/                     # запись, replay, калибровка
  tests/                     # unit, integration, replay
  docs/                      # hardware inventory, runbook
```

Рекомендуемый раздел ответственности: Python для VLM, API и оркестрации; C++ для SDK bridge. Реализация контроллера выбирается после измерения задержек. Зафиксировать версии зависимостей и commit SDK после первого рабочего подключения.

## 5. Контракты

VLM получает текст, текущий RGB и при необходимости короткую историю. Разбор языка и визуальный поиск реализовать отдельными вызовами: это позволяет различать их ошибки. Температуру генерации уменьшить, ответы валидировать по схеме.

Пример плана:

```json
{
  "schema_version": 1,
  "task_id": "uuid",
  "steps": [
    {"skill": "face_target", "target": {"kind": "door"}},
    {"skill": "approach_target", "target": {"kind": "door"}}
  ]
}
```

Разрешённые навыки: `stop`, `turn_relative`, `walk_distance`, `look_around`, `face_target`, `approach_target`. Не более двух шагов. Единицы: метры, радианы, секунды. Скорости и дистанцию остановки задаёт контроллер из конфигурации, а не свободный текст модели. Численные аргументы проверяются по диапазонам.

`TargetObservation` содержит `frame_id`, время получения, `track_id`, описание, bbox/mask, bearing, метрическую дальность при наличии и признак валидности. VLM не назначает дальность по RGB. Число confidence от VLM не считать калиброванной вероятностью; пороги выбирать по тестовому набору.

`RobotState` содержит позу, ориентацию, скорость, состояние SDK, возраст сенсорных данных и текущего владельца управления. Для времени аренды использовать локальные монотонные часы робота; не сравнивать напрямую монотонные часы разных машин.

## 6. Порядок разработки

### Шаг 1. Подключение и SDK bridge — 2–4 рабочих дня

Собрать официальный пример AS2 отдельно от приложения. Проверить чтение состояния и передачу управления между SDK и оператором. Затем реализовать `get_state`, `request_control`, `send_velocity`, `stop`, `release_control`.

Сначала выполнять всё через mock bridge; реальные команды включать явно. Ошибки SDK сохранять в журнал. Не использовать `Damp()` как универсальную остановку: выбрать штатную процедуру по документации AS2.

Готовность: оператор может прервать управление, а при пропадании управляющего процесса робот прекращает движение проверенным способом.

### Шаг 2. Сенсоры, запись и replay — 2–4 дня

Получить RGB, облако точек/глубину, одометрию и IMU. Привести их к общей системе координат. Проверить intrinsics камеры, extrinsics камеры и LiDAR относительно корпуса и временное совмещение при повороте.

Реализовать `record_episode` и `replay_episode`. Сохранять исходные данные, времена, инструкцию, выходы VLM, запросы навыков, фактическое движение, вмешательства и итог. Ограничить объём диска и срок хранения видео с людьми.

Готовность: одна запись воспроизводится без робота; направление и дальность контрольного объекта совпадают с измерением на площадке.

### Шаг 3. Навыки движения — 3–5 дней

Реализовать поворот по yaw, ходьбу по одометрии, остановку, отмену, таймаут и обнаружение отсутствия прогресса. Начать с небольших скоростей; конкретные пределы утвердить испытаниями AS2.

Начальные частоты проектирования: контроллер 20–50 Гц, VLM по событию или примерно 0,5–2 Гц. Частоту отправки в SDK выбрать по документации и измерениям. Контроллер не должен ждать ответа VLM.

Watchdog исполняется локально: истекла аренда, устарели сенсоры, потерян контроль или обнаружено препятствие в тормозном коридоре — остановка. Длину коридора определить по скорости, измеренному тормозному пути и запасу. Учесть полный габарит корпуса.

Готовность: поворот и ходьба выполняются с заданными допусками, а потеря внешнего GPU-компьютера приводит к остановке.

### Шаг 4. VLM и понимание инструкций — 2–4 дня

Сделать заменяемый backend модели. NaVILA использовать как кандидат для навигации; проверить его на ваших кадрах и русских приказах. Другой готовый instruction VLM допустим, если он лучше выдаёт валидные планы и находит цели в ваших условиях.

Для простых численных команд можно использовать детерминированный parser перед VLM. Проверять неизвестные навыки, отрицания, неоднозначные цели и последовательность двух действий. До движения запускать в режиме `dry-run`: план и цель показываются оператору, SDK не вызывается.

Готовность: тестовый набор из 50–100 приказов даёт корректные планы; неподдерживаемые команды возвращают явный отказ, а не случайное движение.

### Шаг 5. Поиск и удержание цели — 3–6 дней

Белая стена: выделить область стены, подтвердить цвет внутри неё, получить геометрию поверхности из глубины/LiDAR. Дверь: локализовать область двери и определить точку подхода перед ней. Человек: локализовать кандидатов и удерживать выбранного трекером.

VLM bbox использовать как начальное предложение. Для навигации уточнять маской/детектором и геометрией; брать устойчивую оценку глубины по целевой поверхности, исключая фон и выбросы. Выбирать свободную точку перед поверхностью, а не координату внутри стены.

Фраза «мужчина» используется как визуальное описание цели, без установления личности. Если подходящих людей несколько или описание ненадёжно, запросить уточнение, например «человек в синей куртке». Для поворота к человеку метрическая глубина не обязательна, но необходим устойчивый bearing.

Готовность: во время поворота цель сохраняет track_id; при исчезновении робот останавливается и выполняет ограниченный повторный поиск.

### Шаг 6. Выполнение задач — 3–5 дней

Автомат состояний: `IDLE -> PARSE -> FIND_TARGET -> EXECUTE -> VERIFY -> SUCCEEDED`. Дополнительные состояния: `NEED_CLARIFICATION`, `FAILED`, `CANCELLED`. Любое движущееся состояние поддерживает отмену и таймаут.

«Дойди до стены/двери»: найти цель, выровняться, выбрать локальную точку подхода, двигаться с обновлением геометрии, остановиться на настроенной дистанции. Для MVP при заблокированном пути остановиться с `PATH_BLOCKED`; обход препятствий добавить отдельной задачей.

«Повернись к человеку»: найти цель, вычислить bearing, поворачивать до углового допуска, подтвердить на нескольких наблюдениях и остановиться.

«Оглянись»: ограниченный обзор, например четыре последовательных поворота по 90 градусов с остановками и кадрами, затем восстановление исходного yaw. Суммарный поворот отслеживать с разворачиванием угла, чтобы переход через ±pi не завершал обзор преждевременно. Эта последовательность является внутренней реализацией одного навыка.

Для двух действий второй шаг начинается только после успешной проверки первого. При повторном подключении незавершённые действия автоматически не возобновляются.

Готовность: все целевые команды выполняются целиком, каждое завершение имеет проверяемую причину.

## 7. План деплоя

Деплой оформляется кодом после проверки ОС, SSH и SDK. До этого все пути и сервисы ниже являются проектом интерфейса, а не готовыми командами для конкретного робота.

| Файл | Назначение |
|---|---|
| `deploy/preflight.sh` | Проверить ОС/CPU, диск, SDK, интерфейс, сенсоры и доступность model server; без движения |
| `deploy/build_release.sh` | Собрать под архитектуру onboard, зафиксировать зависимости и сформировать manifest/checksums |
| `deploy/deploy_robot.sh` | Передать release по SSH, проверить целостность, установить в отдельный каталог и переключить версию |
| `deploy/start_model_server.sh` | Запустить VLM на GPU-компьютере и проверить готовность |
| `deploy/healthcheck.sh` | Проверить процессы, сенсоры, SDK и задержки; без вызова движения |
| `deploy/rollback_robot.sh` | Остановить приложение и вернуть предыдущий release; без автоматического движения |
| `deploy/systemd/*.service` | Запуск bridge/контроллера и журналирование при наличии systemd |

Установка в отдельное пространство, например `/opt/as2-vlm/releases/<version>` с `current` и `previous`; конфиг в `/etc/as2-vlm`, логи в выделенном writable-каталоге. Пути подтвердить после preflight. Не перезаписывать vendor runtime, SDK и глобальные Python-пакеты; использовать собственный venv/runtime. Секреты и SSH-ключи не включать в release.

Последовательность развёртывания:

1. Запустить model server и проверить пример изображения.
2. Выполнить preflight в режиме только чтения; несовместимость завершает установку.
3. Собрать и загрузить release под целевую архитектуру; текущая версия ещё работает.
4. Перевести приложение в IDLE, остановить его штатно и переключить release.
5. Запустить сервисы с `motion_enabled=false` и проверить сенсоры/API/SDK.
6. Прогнать команды в dry-run и сравнить планы с ожидаемыми.
7. Локально включить движение на текущую сессию и проверить STOP, небольшой поворот и короткую ходьбу.
8. Выполнить сценарии подхода под наблюдением оператора.
9. При ошибке откатить release; сохранить журнал неудачной установки.

Автозапуск означает готовность приложения принимать команды. После reboot/restart движение выключено; старые приказы не исполняются. Healthcheck и повторный deploy не захватывают управление роботом. Watchdog не должен зависеть от жизни model server или task executor.

## 8. Проверки и критерии приёмки

Unit: валидация плана, диапазоны аргументов, переходы автомата, cancel/timeout, yaw wrap, lease expiry, дубли запросов. Integration: mock SDK и поток сенсоров, обрыв сети, задержка VLM, устаревшие кадры, потеря цели, сбой процесса.

Replay: записанные сцены с белыми стенами, дверями, людьми, несколькими кандидатами и отсутствующей целью. Отдельные сцены отложить до финального тестирования.

Предлагаемые начальные критерии для согласованной площадки:

- Не менее 18 успешных выполнений из 20 для каждой основной команды; отдельно указать условия и вмешательства.
- Поворот к цели: ошибка до 10 градусов после стабилизации наблюдений.
- Подход: остановка в заданном диапазоне, например 0,8–1,2 м от поверхности; диапазон уточнить испытаниями.
- Обзор: полный заданный угол и возврат с ошибкой до 10 градусов.
- Во всех тестах обрыва связи, отмены и просрочки управления подтверждается остановка; измеряется задержка и тормозной путь.
- Отсутствующая, неоднозначная цель или заблокированный путь дают явный статус, без бесконечного поиска.

Это критерии прототипа в ограниченной среде, а не доказательство надёжности в произвольных помещениях.

## 9. Сроки и порядок приоритетов

Оценка: 4–6 календарных недель для двух разработчиков с опытом SDK/робототехники и VLM при доступных сенсорах, GPU и рабочей документации. Один разработчик или необходимость делать драйверы увеличивают срок.

Неделя 1: inventory, SDK bridge, сенсоры и запись. Неделя 2: навыки движения, watchdog, mock/replay. Неделя 3: VLM, поиск и трекинг. Неделя 4: подход к целям и задачи из двух действий. Недели 5–6: воспроизводимый деплой, испытания и исправления.

Первый вертикальный результат: «повернись к двери» от текста до реального поворота. Второй: «дойди до двери». Третий: перенос на белую стену и человека. Обучение/LoRA добавляется только после анализа накопленных ошибок; для работоспособного MVP оно не является обязательным этапом.
